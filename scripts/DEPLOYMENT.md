# 部署前准备与验收

当前代码具备密码登录和数据库会话基础，但尚未完成生产部署。本文记录本仓库需要核验的条件，不代表已部署。

## 部署目标待确定

需要确定运行机器/操作系统、对外域名与HTTPS终止位置、PostgreSQL部署位置，以及独立清理任务运行身份。没有这些信息，不能给出可直接执行的反向代理或服务注册配置。不要把本机开发.env直接搬到公网。

## 配置与启动顺序

1. 准备独立数据库和受限应用账号；迁移由具备建表权限的部署身份执行。测试使用独立TEST_DATABASE_URL，不对生产运行固定账号E2E。
2. 通过目标环境安全配置注入DATABASE_URL、APP_ENV=production、DEBUG=false、AUTH_COOKIE_SECURE=true和至少32字符的随机AUTH_SECRET。生产校验目前即使关闭短信也要求AUTH_SECRET。不在文档或日志中粘贴真实配置。
3. 当前不具备短信资质，保持SMS_PROVIDER=disabled、ALIYUN_SMS_ENABLED=false。默认同源部署时CORS_ORIGINS=[]；确需跨域时按实际浏览器来源精确配置，并额外验收Cookie行为。
4. 备份并实际验证恢复路径，记录备份/WAL中敏感数据的保留期限。再执行python -m alembic upgrade head，核对current/head均为0014_trip_return。
5. 初期使用单个应用worker，关闭开发热重载；WebSocket广播仍为进程内。仅向可信反向代理开放应用监听端口，并按实际代理地址配置转发头信任范围。
6. HTTPS代理需支持WebSocket升级，并正确传递Host/协议信息；用最终域名验证Cookie Secure、Origin检查和WebSocket连接。
7. 为独立清理进程配置不依赖交互用户登录的服务身份、自动重启和外部告警。本机Windows任务不能作为生产无人值守清理的验收依据。详见[清理说明](AGENT_RETENTION.md)。
8. 对/health设置进程存活检查，对/ready设置数据库就绪检查；独立监控清理心跳及失败。/ready不验证迁移版本、地图、LLM或备份。

## 上线验收

- 注册8～15位密码账号，登录、刷新恢复、昵称和旅游偏好保存，刷新不自动打开旧Trip。
- 两个独立客户端登录同账号；退出其他会话后当前客户端有效，另一个HTTP请求失效，WebSocket在既有检查周期内关闭。会话数可能多于设备数。
- 改密后所有旧会话失效，当前新会话可用；旧长密码账号仍能登录并改为新规则。
- 成员加入与权限、双客户端实时更新、创建者确认/重开和版本失效；地图失败明确展示估算。
- 数据库异常时/ready返回503且不泄露细节；/health仍表示进程存活。故障注入仅在预发布隔离环境进行。
- 停止Web服务后独立清理仍工作；清理故障产生告警，恢复后继续清理。清理延迟和备份保留边界得到确认。
- 首次GitHub云端回归通过；当前仅本地测试通过，工作流尚未推送执行。

## 发布与恢复

发布记录必须包含提交版本、配置版本（无真实密钥）、迁移版本及验收结果。应用回滚须先核对数据库兼容性；不要直接在已有业务数据的数据库执行Alembic降级或清库。先在预发布验证恢复备份和重新部署流程。

目前尚未自动提交、推送或部署。账号自助找回、会话逐项设备管理、跨worker广播仍为后续任务。
